# Deployment scope and limits

- This is a lab deployment baseline, not a claim of a production audit. HTTPS is provided at Front Door. The origin hop and internal tier traffic use HTTP until you add an origin certificate and HTTPS listener/settings. Production requires verified end-to-end TLS, monitoring/alerts, application/database authorization, tested release promotion, and operational ownership.
- Azure Front Door origin traffic is limited by the ingress NSG service tag. At the edge stage nginx additionally checks the specific X-Azure-FDID. The pipeline updates existing web instances; the VMSS template includes the guard for newly created instances. Cloud-init/template changes do not automatically reconfigure existing Flexible VMSS instances in manual upgrade mode. The guard does not affect /health because that route exposes no application data.
- Outbound defaults remain permissive for package installation and Azure services. Tier NSGs control inbound tier communication. Add explicit outbound restrictions after identifying package repositories, DNS, monitoring, and SQL endpoints.
- App VMs access SQL through private endpoints. SQL is Entra-only and its public network is disabled. The demo returns JSON but does not query SQL. No SQL password is put into Terraform or VM custom data.
- SQL zone redundancy and HA replicas are Azure managed. The diagram's SQL icons are logical representations. Front Door DNS default hostname works without a purchased domain. A custom Azure DNS zone requires a domain you own and registrar delegation; never use the reference image's domain unless you own it.
- Web/app subnets are regional and the two compute zones share them. The deployment uses one Standard NAT for each tier, not guaranteed zone-redundant egress. Enabling fewer NAT/Bastion resources can reduce cost but changes architecture behavior. `enable_nat=false` requires another explicit egress path; otherwise cloud-init package downloads can fail.
- Flexible VMSS backups are enabled through an idempotent reconciliation script after apply. Run BACKUP_RECONCILE regularly with the last deployed ROLLOUT. Instances added by autoscale remain unprotected until reconciliation; check instance protection status and first recovery points. Automatic Azure Policy protection is an additional production hardening task.
- Autoscale controls instance count, so Terraform ignores VMSS `instances` drift. Change the autoscale profile minimum/default for deliberate capacity changes and validate actual zone placement.
- Terraform state is local on the persistent Jenkins node at /var/lib/jenkins/terraform-state/kt-lab. Workload and bootstrap have separate state files. Restrict directory permissions, back up the agent disk, and retain state when clearing the workspace. The pipeline makes local snapshot copies; copies on the same disk do not survive loss of that disk. Assign terraform-local to only one node and use one job for this environment. Local Terraform file locking does not coordinate separate hosts.
- Jenkins binds a service principal client ID, client secret, tenant ID and subscription ID from its credential store to ARM_* environment variables. The service principal has Contributor on the three dedicated workload resource groups. It cannot grant RBAC roles. Bootstrap is run by an operator with permission to create resource groups and role assignments. Keep credentials out of plain Jenkins global properties, Git and Terraform variable files; rotate the Jenkins secret before expiration.
- This workspace successfully installed the pinned provider and ran `terraform fmt -check`. `terraform validate` could not start the provider because Unix sockets are prohibited here. Jenkins must successfully run validate, an Azure-authenticated plan, and smoke tests before deployment can be considered verified. No Azure deployment was run in this workspace.
